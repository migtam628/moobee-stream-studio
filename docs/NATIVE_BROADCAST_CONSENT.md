# Native broadcast consent — developer acceptance
The real-test start command remains disabled in normal builds. In an explicitly enabled acceptance build, typed confirmation and destination revision review are followed by an OS-native affirmative confirmation (AppKit on macOS, Win32 MessageBox on Windows) before capture, vault lease acquisition or publisher connections. The native dialog summarizes destinations, duration, selected source categories, profile, bitrate and optional recovery behavior; it does not display the key. Untrusted destination labels are escaped on one line. Cancel/No is the default. A process-wide prompt slot prevents overlapping prompts. The caller expires approval after 90 seconds and rechecks the session before capture; a late click cannot start that expired run. The OS modal may remain visible until dismissed; in-flight native dialogs cannot be forcibly dismissed by a renderer Stop. No production Go Live or external API start command is enabled.

This is an independent native user-interaction step, not a full defense against a malicious local process or OS-level input automation. It summarizes source categories rather than independently rendering or validating the scene preview. Physical manual QA must confirm the dialog is readable on both platforms, Cancel/No and closing the dialog send no media, expiry and cancellation do not start capture, a second prompt cannot overlap, destination edits invalidate stale reviews, and explicit approval starts only the reviewed private test destination. CI links the acceptance-enabled code and checks summary validation; it does not interact with real OS dialogs or send a stream.
