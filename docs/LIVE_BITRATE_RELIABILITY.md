# Workstream 10 — bitrate reliability

The developer-only native acceptance interface offers an explicit **Lower bitrate after reconnect** option for a single saved destination. It defaults off. Confirmation freezes the option with the selected capture and destination; the backend rejects the option for multiple destinations. A classified transient transport failure can initiate the existing bounded recovery policy. A fresh encoder epoch uses the next lower supported video preset (6000 → 3000 → 1500 kbps, or 3000 → 1500 kbps); no automatic upshift, no mid-epoch reconfiguration and no additional retries are introduced. Resolution, frame rate, audio, selected destination and authorization stay unchanged. A retry that ultimately succeeds still fails uninterrupted acceptance. The option does not claim that a transport error was caused by insufficient bandwidth.

Analytics shows the initial/current target and a recommendation when the same sending destination has sustained queue pressure (4 MiB or 96 packets) for three seconds with sample gaps no longer than 1.5 seconds. Separate healthy queues are not summed into a false recommendation, and failed/reconnecting destinations are excluded. Recommendations never change a running encoder. They are sender-side observations, not a bandwidth test. Multistream recovery preserves its shared encoder settings.

Unit tests exercise preset boundaries, opt-in policy, continuous per-output pressure, missing samples, alternating outputs and interrupted acceptance. Browser smoke tests exercise the reviewed flag and advice display. Real native encoder behavior after recovery, rate control under constrained network conditions, automatic in-place adaptive bitrate, dropped-frame recovery, capture-device reconnection, persistent diagnostic history and physical soak tests remain outstanding. The ordinary production build remains gated. No actual broadcast, installer or release initiated.
