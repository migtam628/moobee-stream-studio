# Native streaming soak diagnostics — priorities 9.4 and 9.5

The explicitly enabled native streaming acceptance build samples its own process CPU and resident memory approximately once per second using sysinfo's OS process counters. A separate thread avoids placing system inspection in the encoding loop. The first successful sample establishes the resident-memory baseline; subsequent samples track current and peak sampled resident memory, CPU and sample age. CPU is 100% per logical core and may exceed 100%. Browser/WebView helper processes, GPU usage and allocations between samples are excluded. The first CPU sample and unavailable process readings are not invented. Sampling stops cooperatively when the native session ends or cancellation is requested; summaries remain available until a new session replaces them. The native sampler retains aggregate values only. A separate renderer-side, bounded redacted history samples these observations while the app is open; no telemetry is sent externally.

The native Program sink also measures encoded packet counts, approximate last video and AAC packet-end times, signed video lead and maximum absolute gap, pending AAC encoder frames, PCM supplied, Windows missing source frames and slowest measured encode tick. The media-end estimates use nominal frame/block duration rounded down to whole milliseconds; an encoded video lead is not a hardware synchronization or lip-sync measurement. A/V counters reset on whole-encoder recovery; independent destination recovery remains visible separately. Mac missing-source frames are not measured and remain unavailable. Audio-disabled sessions do not invent AAC timing. Encode timing excludes capture/compositing and fanout. Packet counters reflect produced media, not decoded output or delivery.

## Acceptance procedure (not yet executed)

1. In a developer-only acceptance build, select a private RTMPS receiver and verify a short test with the intended display/capture card and audio source.
2. Open Analytics during a 5-, 30-, then 120-minute test. Record sampled CPU/RSS baseline, peak and final measurements, sample count/age, sender queue, late frames, A/V packet gap and pending audio. Note hardware, OS, profile and selected sources.
3. Independently observe receiver video/audio and measure actual A/V offset at the beginning, middle and end using a visible/audible synchronization reference. Inspect receiver continuity and session termination. Resource values are observational, not universal pass/fail thresholds.
4. Record any retries, stalls, missing-source frames or unexpected termination. Do not mark an interrupted stream as an uninterrupted soak. Never include stream keys in evidence. Repeat separately on macOS and Windows, then test multiple destinations.

Unit tests validate aggregation and timing math; browser smoke tests mock readings only. Real process sampling accuracy, native encoder load, capture-device timestamps, GPU and total app-process resource usage, receiver decode and true lip-sync remain unverified. No real stream, installer or release was initiated.

## Redacted sender report
Open Analytics > Local sender diagnostic history > Prepare redacted sender report, then copy the JSON to your own evidence file. The latest native session retains at most 960 allowlisted observations in renderer memory, approximately every ten seconds or on observed status/reconnect/bitrate changes. Tab navigation does not reset the collector. Reload, application exit, a new native session, polling gaps or sample eviction can lose evidence; this is not a persistent or complete event log. The report excludes stream keys, URLs, names, destination IDs and session IDs. Report preparation and copy are explicit, with no background upload. Preserve the independently received capture, actual sender build commit, manual A/V checks and receiver report separately. No real-device acceptance is inferred from sender history.
