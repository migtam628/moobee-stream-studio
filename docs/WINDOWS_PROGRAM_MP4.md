# Priority 6A — Windows native Program MP4 (experimental)

The Windows MSVC desktop build statically links MooBee's own C++ Media Foundation sink adapter, using the Windows SDK and OS H.264 encoder/MP4 sink. Rust supplies bounded RGBA-to-NV12 conversion and a nominal frame clock. No OBS, Streamlabs, FFmpeg executable or runtime helper is required. A working OS Media Foundation installation and compatible H.264 encoder are prerequisites; Windows N editions may need the official Media Feature Pack.

The shared Program capture worker supports silent display-only H.264 MP4 with one to four existing XCap monitor inputs, grid/PiP, source transforms/filters and static overlays. Profiles: 640x360/10, 1280x720/15 and 1920x1080/30; bitrate presets 1500/3000/6000 kbps. Duration 2–60 seconds. Pause, resume, early stop, same-input native scene Takes and live nominal statistics use the existing session controller. Windows does not yet support native camera/capture-card inputs, audio or AAC, application/window capture, segmented sessions, or separate webcam inset. Unsupported options are rejected rather than silently omitted. The AVI fallback remains.

Output uses the common private UUID temporary/ready/final MP4 storage: structural validation, measured container duration, 64 MiB file cap, no-replace publication and explicit finalized-file recovery. Free-space thresholds are 96 MiB before startup and 16 MiB on periodic checks. Incomplete clips are not published. Media Foundation WriteSample and Finalize are synchronous and do not yet have an independent timeout; a stalled OS encoder may delay stop. Target bitrate, nominal fps and container structure do not prove real-time performance or playback.

CI: Windows native bridge compile/link; NV12 known-color/geometry tests; shared container, storage, session and source-transform tests; explicit synthetic Media Foundation MP4 encode/finalize test; simulated Windows UI IPC checks. The synthetic test needs an encoder available on the CI host. No actual monitor, camera or audio hardware is exercised by it.

Physical acceptance: on Windows 10/11 with Media Foundation, record each profile and bitrate, inspect actual frame rate and colors, decode the complete MP4 independently, test pause/resume/stop, filter parity, same-input Takes, low disk space and failed publication. Measure CPU, latency, dropped/repeated frames and encoder stalls. Confirm the fallback AVI still works, including when MP4 initialization fails. Windows audio, device enumeration and A/V synchronization are separate milestones. No installer publication or execution is requested.

## Priority 6B — Default endpoint audio and AAC (experimental)
Opt-in microphone and desktop audio use the Windows default console capture and playback endpoints through shared-mode WASAPI. The desktop endpoint is opened in loopback mode; no per-application isolation is provided. Shared-mode conversion requests 48 kHz stereo PCM16. Unsupported format/device, permission, disconnect and queue-overrun failures are returned; no automatic endpoint substitution occurs. A bounded one-second queue per source is polled once per media tick. A shortfall is padded with silence and counted as missing source frames (desktop inactivity can also produce a shortfall); these counters do not measure all device discontinuities or clock drift. While paused, pending PCM is discarded; gain and mute are configured before capture. The first tick may contain silence while devices start. The shared Rust mixer produces aligned float PCM and Media Foundation encodes AAC-LC at a 128 kbps target, on the same nominal timeline as H.264. Finalization requires the exact submitted PCM frame count for the video frame count. Live recording telemetry shows mixed PCM peak and missing source frames. Silent MP4 remains available when both inputs are disabled.

At the 6B milestone, named endpoint selection, HDMI audio enumeration, idle live meters on Windows, device-clock synchronization/resampling beyond OS format conversion, continuous independent audio draining and drift correction remain future work. Test hardware startup, physical mic, desktop playback, both inputs together, clipping, mute, pause/resume and device disconnect; decode both tracks independently and compare visible/audible markers. A synthetic H.264/AAC test checks duration and MP4 sample-entry markers, not real device capture or independently decoded playback. Existing limits on duration, camera inputs and file size remain. No installers requested.

API references: https://learn.microsoft.com/en-us/windows/win32/medfound/aac-encoder and https://learn.microsoft.com/en-us/windows/win32/coreaudio/audclnt-streamflags-xxx-constants.

## Priority 6C — Named Windows audio capture endpoints (experimental)
The Audio Mixer discovers active Windows capture endpoints through IMMDeviceEnumerator, with friendly names and opaque endpoint IDs. Discovery does not open a recording or request PCM. Select a named microphone and a different named USB/HDMI capture-card audio endpoint, plus optional desktop audio via the default playback loopback. The mixer supports up to three sources. Named capture inputs are opened by their exact ID, with active-state and capture-direction checks; failures never silently substitute a default endpoint. Refresh preserves unavailable Windows selections so they can be corrected explicitly. Device names are not proof of an HDMI signal. Capture cards must expose their audio as an active Windows capture endpoint. Desktop playback selection remains default-only.

Tests cover named input validation, UTF-16 endpoint IDs and Unicode labels, duplicate rejection, and simulated Windows UI-to-native routing of three audio sources. Physical testing must verify enumeration, distinct sources, removal/reconnection, actual signal, AAC playback, clipping, pause/resume and synchronization. Pre-recording Windows meters, independent clock drift correction and Windows camera/capture-card video remain outstanding. No installer builds or publication requested.

References: https://learn.microsoft.com/en-us/windows/win32/coreaudio/device-properties and https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nf-mmdeviceapi-immdeviceenumerator-getdevice.

## Priority 6D — Windows idle audio meters
Opt-in local metering uses a dedicated MTA thread, 20 ms PCM blocks, bounded latest results, a five-second inactivity lease, gain/mute updates and explicit release before recording. Pre-recording peaks are not playback or recording-time per-input telemetry. Device startup, driver teardown latency, clock drift and physical audio still require validation. No installers requested.
